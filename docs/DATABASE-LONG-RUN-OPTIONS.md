## 事实边界与新的判断

用户明确指出：过去约 12 小时只是两次观察之间的时间，实际进入游戏运行只有几分钟，数据库却从约 160 MiB 涨至约 1.84 GiB。**不得把这 12 小时当成实际游戏运行时长，不能据此计算每小时模拟写入量。** 后台是否仍在调度、哪些世界实际运行以及增长由哪些表产生，由主线程核实；本研究不替代时间线证据。

主线程随后提供的独立证据：一个“规则55年”演示世界仍为 running，其他 28 个世界暂停；该演示世界从 day 19834/hour 21 到 day 20184/hour 21，增加 350 个模拟日。在 speed=1、secondsPerDay=120 时对应约 11 小时 40 分钟的后台推进，世界主表约 42024 个版本也与此接近。这说明“用户观看几分钟”与“另一个演示世界后台推进很久”可以同时成立；不能改写成用户实际玩了 12 小时，也不能仅据此断定暂停按钮失效。具体 pause 操作对象及探测结果由主线程报告。

用户现已明确选择：**关闭页面或无人观察时，自动保存并暂停；回来后手动继续。** 这一运行契约应先在现有架构内修复，不需要为了 inactivity 重构整个应用。

现有 `worldStore.ts` 将数组拆块，仅写变化块，但仍在 Convex 中更新核心文档；`tick` 通过服务端 scheduler 执行 `heartbeat`。拆块和压缩可以减少每次写入，却没有取消 Convex 的技术版本保留，也没有单独约束后台何时继续模拟。因此不能把上一轮改造当成已经解决长期增长和启动 RAM。

同样，`events.slice(-70)`、样本降采样或活人物列表等**业务数组限长，不等于技术 MVCC 版本限长**。即使当前对象大小不变，反复更新仍会产生后端版本；反过来，缩短 MVCC 窗口也不会自动给持久业务历史设置期限。

需要分别保存三种东西：

1. **当前准确进度**：完整状态、模拟时间、RNG、ID 计数器、人物及关系、资源账本、计划、决策及租约。它是恢复游戏的权威数据。
2. **用户可见的已产生历史**：原有事件、人物档案、决策、计划、统计及分支关系。不得以年度摘要替换后删除精确原记录。
3. **技术恢复记录**：为事务、崩溃恢复或短期撤回服务的旧版本和 journal。用户没有要求永久保存每个底层版本；它们应有明确边界。

前两项随真实内容增长可以合理增加；第三项不应仅因为保存了很多次同一个世界，就无限累积。保存准确进度也不等于必须保存每次写入的全部历史副本。

## 最多三个候选

| 候选 | 用途与优先级 | 主要改造成本 | 主要边界 |
|---|---|---|---|
| 1. 自有 SQLite 当前状态 UPSERT + 独立历史表 | **Windows 单机主推荐**；每次提交更新当前进度，业务历史另存 | 中到较高：本地服务、订阅与调度迁移、数据导入和恢复验证 | 单写入服务；需要维护自己的 API，历史内容仍会合理增长 |
| 2. 周期快照 + 有界应用 journal | 需要有限撤回、分支或高频存档时，在方案 1 上增加 | 更高：日志协议、检查点、截断、格式版本 | 不应为了当前需求立即建立完整事件溯源系统 |
| 3. 继续 Convex，验证回收窗口和后台生命周期 | 最小架构变更、需要现有实时订阅时的过渡方案 | 初期较低，但回收和旧版启动问题必须专项验证 | 不能仅凭降低 retention 宣称大小或 RAM 已可控 |

## 候选 1：应用自有 SQLite 存档，更新当前状态

SQLite 官方将其定位为可承载完整应用文档的文件格式，支持事务及持续增量更新；UPSERT 可按主键更新现有行。[应用文件格式](https://www.sqlite.org/appfileformat.html)、[UPSERT](https://www.sqlite.org/lang_upsert.html)

建议让独立 Node 服务唯一拥有文明模拟和写入权，SQLite 数据文件放 E 盘。保留当前 TS 纯模拟引擎；不重写规则或随机算法。`engine.ts`、`clock.ts`、`random.ts` 没有运行时 Convex 导入，现有 `splitWorld/joinWorld` 也能继续作为无损存储适配。原聊天小镇可继续使用 Convex。

最小数据模型是当前世界核心、当前人物/地图等状态、业务历史、命名存档和分支引用。当前状态按稳定 ID UPSERT，已终结历史按原业务 ID 写入，只有用户命名保存或明确的恢复策略才创建旧检查点。即使第一版仍以完整 JSON 保存每个世界当前状态，也无需为每次提交新增一份永久历史行；后续再按实际性能需要拆表，避免一开始就把所有属性拆成很多行。

每次成功的模拟提交，应在**同一事务**内保存新状态、RNG、clock 的小时及预算、nextId、新业务历史与 revision；提交成功后再向界面确认。提交失败则继续使用上次已提交状态，不能把尚未持久化的可变内存状态当成已保存进度。模拟步长不必等于渲染帧率，关键 AI 结果及人工操作仍需提交；不能用降低画面流畅度代替存储治理。SQLite 的原子事务保证整笔提交或整笔不生效。[事务](https://www.sqlite.org/lang_transaction.html)、[原子提交](https://www.sqlite.org/atomiccommit.html)

### WAL、回收与 RAM 如何受控

- WAL 是 SQLite 的事务恢复机制，并不是永久业务时间线。保留自动 checkpoint，限制单笔事务，避免长读事务阻止 checkpoint。默认自动 checkpoint 阈值约 1000 页，但它是触发条件，**不是 WAL 大小的硬上限**；检查点完成也可能复用文件而非立即缩小文件。[WAL 官方说明](https://www.sqlite.org/wal.html)
- 在空闲或正常关闭时尝试 checkpoint，并记录 busy/未完成结果；不要为了缩文件频繁强制 TRUNCATE。长读事务、超大事务或禁用自动 checkpoint 都可能令 WAL 增长。不能手工删除仍可能包含已提交进度的 `-wal`。
- 对“已确认保存”的耐断电要求，可优先评估 WAL + `synchronous=FULL`。`NORMAL` 通常能保持结构一致性，但断电可能丢失最近已提交事务；不能拿这种取舍冒充无损优化。FULL 的实际耗时须本机实测。[同步策略](https://www.sqlite.org/pragma.html#pragma_synchronous)
- 主库释放的空页默认可重复利用，文件未变小不等于仍在新增有效内容。若需要逐步把空闲页交还文件系统，可在新库建表前选择 INCREMENTAL auto-vacuum，后续小批执行 incremental_vacuum。它不是自动删除旧业务数据的开关，也不会压缩仍然存在的记录。[空间回收](https://www.sqlite.org/pragma.html#pragma_auto_vacuum)
- 启动只读取目录、选中的世界和必要尾日志，历史查询分页；不能再遍历全部旧版本或一次加载所有世界历史。SQLite 页缓存大小仅约束该缓存，不是 Node 进程总内存上限；实际 RAM 仍取决于当前活跃世界和 JS 对象。[缓存设置](https://www.sqlite.org/pragma.html#pragma_cache_size)

本机只读核查到 Node 为 `v24.21.0`，`process.versions.sqlite` 为 `3.53.4`。Node 24 官方接口有 `node:sqlite`、`DatabaseSync` 和备份 API，可复用已安装运行时；无需为验证方案先安装 Docker、WSL 或另一个数据库服务。模块目前处于 release candidate 状态，需锁定运行时并验证实际 API；同步数据库操作应由独立服务/工作线程承担，避免阻塞前端。[Node 24 SQLite 文档](https://nodejs.org/docs/latest-v24.x/api/sqlite.html)

**成本判断：** 这不是把连接字符串换掉。需要替换文明的 Convex mutations/queries/scheduler 适配层、实时数据通知和 AI 回调入口。不要把 Convex 与新库同时设成权威写入源；若继续同步列表摘要，摘要只是可重建投影。由于模拟引擎本身可复用，迁移比重写游戏规则更可控，但尚无工期或性能保证。

## 候选 2：有界 journal + 周期快照，借鉴游戏存档与 Fossil

只有需要短期撤回、细粒度恢复或大量分支时，才值得在方案 1 上增加这一层：保留一个已确认的当前检查点，加上检查点之后有限数量/大小的状态变化记录；达到边界后生成并验证新的检查点，再移除其覆盖的技术尾日志。启动只读最近检查点和有限尾部，不能从创世开始重算。

检查点及日志截断的边界必须由序号与事务决定，不仅看文件日期。正在被存档或分支引用的检查点不得回收。既有历史事件与已故人物档案属于业务历史，不能因 journal 截断一起删除。若短时间事件过多，应提前做检查点或暂停并提示存储失败，不能丢掉已经对用户确认的进度。

**可以直接复用的机制：** SQLite Session Extension 支持记录并应用 changeset；Node 24 提供 `createSession`、`changeset`、`applyChangeset`，不必先自写二进制补丁协议。它要求有主键、兼容表结构及起始数据；changeset UPDATE 包含被改列的新旧值，**不是任意 BLOB 的字节差分**。如果一个巨大 JSON 列发生改变，它仍可能携带大块新旧值，未必省空间；session 内部追踪也要按批关闭，不能无限积累。它不自动提供耐崩溃日志和 checkpoint 截断协议。[SQLite Session Extension](https://www.sqlite.org/sessionintro.html)、[Node changeset API](https://nodejs.org/docs/latest-v24.x/api/sqlite.html#databasecreatesessionoptions)

Fossil 有两点适合借鉴：不可变内容按哈希寻址，多个检查点/分支引用相同内容；压缩或 delta 只是磁盘表示，读取时恢复原内容。Fossil 使用 SQLite、zlib 和 delta，且 delta 有目标长度及校验。可将这些用于命名存档、历史归档或分支共享，而不把每秒的热状态都存成永久 artifact；Fossil 自身保存长历史，不是替游戏自动限制存储的现成引擎。[Fossil 格式](https://fossil-scm.org/home/doc/trunk/www/fileformat.wiki)、[Delta 格式](https://fossil-scm.org/home/doc/trunk/www/delta_format.wiki)

普通游戏存档也会明确列出要持久化的对象和字段，而非把所有运行时状态都无限版本化。Godot 的公开存档教程提供此思路，但没有替本项目解决事务、关系完整性或断电恢复，不能直接移植示例后宣称可靠。[Godot 存档教程](https://docs.godotengine.org/en/stable/tutorials/io/saving_games.html)

**准确性边界：** 如果 journal 记录实际写入结果，恢复不需重新调用 AI；如果只记输入再重演，则必须同时固定引擎/规则版本、随机状态、全部外部决策和执行顺序。仅有种子、叙述事件或年度摘要不足以准确恢复当前进度。当前需求没有要求所有历史时刻逐小时回放，因此不建议为了迁移先实施完整 event sourcing。

## 候选 3：保留 Convex，但必须验证技术版本回收

固定后端 `precompiled-2026-10-10-72ce13c` 的源码默认 `DOCUMENT_RETENTION_DELAY=14天`，`INDEX_RETENTION_DELAY=4分钟`。这是后端时间的技术窗口，不是游戏内经过的天数。后端进程停止时不会继续执行自己的清理任务；到了某个时间并不代表磁盘文件会自行变小。[固定版本参数源码](https://github.com/convex/convex-backend/blob/72ce13c/crates/common/src/knobs.rs)

缩短技术旧版本窗口不会按设计删除用户表中的最新活文档，也不等于删除业务事件历史；但旧快照读取、导出及回收游标会受影响。上游 [issue #358](https://github.com/convex/convex-backend/issues/358) 报告过先缩短再放大窗口造成回收循环；这只是上游报告，不能据此断言本机一定触发或已经修好。不要照搬其直接修改内部元数据的绕过办法。

这个固定 SQLite 后端的启动路径还会为 `max_ts` 提前加载整个 document log，忽略调用者请求的单页大小。业务拆块减少写入量，但旧版本数量仍可能影响启动；单改保留参数也不能让回收 worker 在失败的启动之前先清理。[SQLite 固定实现](https://github.com/convex/convex-backend/blob/72ce13c/crates/sqlite/src/lib.rs#L403)、[max_ts 调用](https://github.com/convex/convex-backend/blob/72ce13c/crates/common/src/persistence/mod.rs#L645)、[上游 issue #593](https://github.com/convex/convex-backend/issues/593)

若选择这条路线，应先在新建的小型隔离库使用**固定不反复调整的试验窗口**，受控写入同一文档的多个版本，并持续运行跨过该窗口，核对：最新完整业务值与类型不变、内部版本数确实下降、回收游标持续推进、没有 out_of_retention 重试、文件空闲页能够复用、随后冷启动 RAM 和耗时可接受。观察文件大小一项不足以验收。此前六小时窗口试验未完成启动和回收，不构成成功证据。本轮不提出任何未经验证的生产参数。

## 应不应该把高频文明状态迁出 Convex

**以 Windows 单机、长期运行和准确存档为主要目标，建议把文明高频热状态迁到应用自有 SQLite。** Convex 可以继续承载原聊天小镇或低频、可重建的展示数据。此判断基于数据生命周期与固定后端行为，不是根据“12 小时一直运行”的错误前提，也不是宣称迁移即可消灭任何增长。

主线程已经发现用户未意识到的后台持续执行，应先按用户本轮选择修复自动保存暂停，再实施或比较迁移；否则换库后仍会产生不符合用户意图的新历史。此次生命周期修复与迁移可以分开验收，无需为解决关闭页面继续运行的问题先重构整个 app。

### 下一步可验证的迁移边界

1. **范围仅限文明写入链路。** 保留原 `convex/aiTown` 聊天小镇、原聊天消息/记忆、Ollama 配置和 Windows 使用入口；复用文明 TS 引擎、RNG、地图与人物呈现。前端只替换文明数据访问适配，不重新设计导航和所有页面。迁移不能同时运行两个模拟权威或后台循环。
2. 在独立库导入所有现存文明、命名存档、分支和精确历史，保留 ID 字符串、人物关系、RNG、时钟预算和进度；已有压缩内容需要解码后对照，不能只迁界面最近可见的记录。先核对全量业务值和引用，再进行任何生产切换，旧库与一致备份保留。
3. 使用同一个暂停世界快照和同一组受控操作，对照现有 Convex 分块存储与 SQLite UPSERT 的提交次数、实际磁盘增长和峰值内存；AI 对照使用已经记录的实际结果或明确标记的规则模式，不将不同模型随机输出当作相同输入。原本没有实际状态变化的操作应避免重复改写大状态；暂停世界不应继续产生模拟状态提交。
4. 在原生 SQLite 单写入服务中验证事务中断、写满/提交失败、正常关闭、强制终止后恢复与冷启动；确认恢复到最后已确认提交的 revision，完整状态/RNG/人物关系一致。分别测主库、WAL、技术 journal、业务历史和命名存档，不以单次压缩率代替长期结果。通过后再决定是否需要方案 2；第一步不用永久 journal 或 Fossil 整套仓库。

实施前至少比较三种状态：明确暂停且服务存活、正常速度真实运行、快进真实运行；分别记录当前状态提交次数、新业务历史数量、主库与 WAL/技术日志大小、冷启动内存、恢复后完整状态/RNG 一致性。压缩率、每小时增长量和“多少年不超多少 MB”都应由这类测量得出，不在研究阶段承诺。

合理的容量模型是：当前活世界 + 精确业务历史 + 明确保留的命名存档 + 有上限的技术 journal + 数据库维护余量。若要求所有已产生业务历史永久保留，总存储仍会增长；目标是让它与真实新增内容相关，并让启动不需要读取整段历史，而不是承诺一个永远不变的文件大小。

## 2026-10-27 隔离可运行试验：600 次真实 heartbeat 与单行 UPSERT

为检验“保存准确当前进度不需要永久保存每个底层版本”，已在 `E:/AI_town/tmp/progress-storage-probe` 完成一个小型独立试验。新建前检查 E 盘剩余约 82.07 GiB；复用现有 esbuild 打包原 `clock.ts`/`engine.ts`，使用已安装 Node 24 的内置 SQLite。未改正式业务代码、源快照、生产数据库或依赖，未启动 Convex 或正式新后端，未调用模型。

输入为主线程提供的暂停快照 `.runtime/storage-20261027/paused-mh7fm2xg8twftrfgzsvkk9bfvh8h1wn4.json` 的完整 `state` 副本。仅在隔离副本将 `running` 从 false 设为 true，表示显式开始这次试验；保留 speed=1、secondsPerDay=120、无 stopDay/endReason。原文件前后 SHA256 一致。
