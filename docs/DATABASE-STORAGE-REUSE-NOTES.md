# 数据增长：可复用方案补充研究

研究日期：2026-10-26。范围：Windows 原生、本地 Convex、SQLite 持久化；仅研究，未安装组件、改业务代码、清理数据或执行迁移。以下兼容性是根据官方接口与现有代码作出的判断，尚未在本项目运行验证。

## 优先结论

最值得复用的是已有 Convex 的调度与业务索引、官方迁移/队列组件、Node 内置流式压缩，以及 restic 的去重备份。没有发现一个安装后就能替本项目自动完成“精确历史保留、压缩归档、分支继承、查询与恢复”的现成组件。归档协议及查询接入仍需要项目代码。

当前 `convex/civilization.ts` 的 `branch`、`lineage` 已通过 `parent`、`forkDay`、`forkSerial` 共享祖先历史并限制读取范围，不能把它描述成每个分支都复制全部历史。扩展归档时应沿用这套截止规则。命名存档仍保存完整 `state`，与分支历史共享是两件事。

## 1. 官方 Migrations / Batch Worker：复用迁移和批处理骨架

**判断：优先复用接口模式；任务复杂后再安装组件。**

- [`@convex-dev/migrations`](https://github.com/get-convex/migrations) 已有分批迁移、进度管理和自定义批次大小，适合将现有大世界文档拆到新表、回填归档索引。默认批次为 100，大文档应调小。业务转换逻辑仍自行提供。
- [`@convex-dev/batch-worker`](https://github.com/get-convex/batch-worker) 提供队列读取/处理、游标、每个命名队列单循环、去抖和故障自恢复，适合持续归档队列。它不自动移动或删除业务记录，处理函数必须自行推进游标或更新记录。
- 官方仓库特别解释了游标的意义：Convex 内部旧版本索引暂存期间，反复从表头取一批再删除会重复扫描已经处理的位置。现有 `crons.ts` 已有分页与调度骨架，小规模维护可以继续复用，不必为了引入依赖重写全部流程。[Batch Worker 说明](https://github.com/get-convex/batch-worker)
- 归档涉及文件写入，不能塞进只负责事务处理的 worker mutation：mutation 领取任务，外部本地进程或 action 处理外部副作用，再以 mutation 确认。组件只能减掉调度样板，不能让文件系统和 Convex 事务天然变成一个事务。[组件接口](https://www.convex.dev/components/batch-worker)

建议归档状态为 `pending → written → verified → committed`：导出固定边界的记录，写临时文件，校验记录数与哈希，发布不可变文件，再按相同边界确认归档。删除热库明细时再次核对版本或只选择已终结记录，避免归档期间被修改的数据丢失。该协议是本项目建议，并非组件内建保证。

## 2. 不可变压缩归档与共享检查点：复用基础库，借鉴设计

**判断：适合本地优先路线，但需要写一个小型归档服务。**

- Node 的 [`node:zlib`](https://nodejs.org/api/zlib.html) 自带 gzip 压缩/解压流，可采用“世界／模拟年份／记录类型”的 `JSONL.gz` 分块，不必新增压缩依赖。主库保留分块位置、时间范围、记录数量、格式版本和内容哈希，历史页按需读取。gzip 的具体压缩率必须用本项目数据实测，不承诺固定倍数。
- 推荐先复用项目现有 Node 启动脚本与 Convex API，新增独立的本地归档进程读写 E 盘；不要在 Convex query/mutation 中直接访问 E 盘。默认 Convex 运行时不是普通 Node，文件系统等能力不能因“本地部署”就假定存在。[Convex 运行时](https://docs.convex.dev/functions/runtimes)
- 文件块一旦确认即不修改；内容相同的检查点可按规范化内容哈希复用，多个命名存档只保存引用。已有分支祖先截止规则应同时用于热记录及归档清单。清理归档必须先考虑所有世界、分支、存档的引用，不能仅按文件年龄删除。此为设计借鉴，尚无本项目成品实现。
- 若要精确回放，需要检查点、全部必要状态变化或可确定性重演的输入、随机数状态、实际 AI 决策结果以及引擎/数据格式版本；现有供界面显示的事件和年度摘要并不满足这些条件。微软的事件溯源模式支持“快照＋事件”思路，同时明确指出全量事件溯源会显著提高迁移和演进复杂度，因此建议只借鉴检查点与变化日志，不立即重构整个模拟器。[Event Sourcing 官方说明](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing)

以后需要远程对象存储时，官方 [`@convex-dev/r2`](https://github.com/convex/r2) 可作为归档文件后端。仓库明确给出 action 中 `r2.store` 写入生成文件、同步元信息与按 key 获取文件的接口；需要 Cloudflare 账号、bucket 与凭据。它既不会自动从业务表归档，也不会自动支持历史查询。目前本地优先，暂不引入账号和外部服务。

## 3. restic：替代反复复制完整备份目录

**判断：值得单独验证的直接复用工具；解决备份占用，不解决运行主库膨胀。**

restic 支持文件内容去重和压缩，重复备份可共享数据；Windows 原生支持 VSS 文件系统快照。仓库可放在本地目录或远端，备份版本仍表现为可恢复快照。[备份行为](https://restic.readthedocs.io/en/stable/040_backup.html)、[本地仓库与压缩格式](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html)

适合沿用项目当前的停机一致性步骤，把同一份完整 `.convex`、代码版本与恢复说明送入 restic，取代每次都保留一个独立全量副本。可设置日/周/月保留策略；`forget` 只移除快照引用，`prune` 才清理不再引用的数据，之后应做仓库检查和恢复演练。[保留和清理](https://restic.readthedocs.io/en/stable/060_forget.html)

注意三个边界：

1. restic 快照是备份，不是产品可直接检索的文明历史数据库。
2. SQLite Online Backup API 能产生一致的单库快照，但本项目 `.convex` 还有搜索、模块和其他 blob 文件；仅备份 SQLite 不证明整套 Convex 存储在同一边界上一致。VSS 解决文件快照与锁定问题，也不应未经恢复验证就宣称具备本项目应用级一致性。现阶段停机完整目录备份更明确。[SQLite Backup API](https://www.sqlite.org/backup.html)
3. 去重节省比例取决于页面变化和备份格式；不要先将每份整库独立压成不同的大压缩包，再期待跨版本得到最佳去重。必须测量真实新增存储、备份耗时和恢复结果。备份若与主库在同一物理盘上，只能解决误操作恢复，不能覆盖整盘故障。

## 4. Aggregate：可选的统计查询组件，不是缩库工具

**判断：后续历史规模大、统计查询慢时再用。**

[`@convex-dev/aggregate`](https://github.com/get-convex/aggregate) 维护可扩展的计数和求和，可按世界/年份组织统计，避免为了总人口变化、事件数量等指标加载全部明细。它需要在业务写入时正确维护聚合数据，并会增加辅助存储，不能自动删除原记录，也不能把当前大文档版本压小。[组件介绍](https://www.convex.dev/components/aggregate)

项目目前样本已经有保留与降采样逻辑；若只展示少量固定年度统计，先用小型年度汇总表更直接。官方建议大结果集采用索引、分页或反规范化，并检查冗余索引；这些优化能省扫描与写入开销，但不要把云端计费的“每个索引视作一份文档”直接当成本地 SQLite 文件一定按相同比例膨胀的证明。[Convex 最佳实践](https://docs.convex.dev/understanding/best-practices/)

## 建议实施次序与验收

1. 先核对现有后端版本回收，测量各类世界状态的实际写入字节和每日增长；这是与长期业务归档独立的问题。
2. 优化高频世界文档，再挑一个暂停世界做本地压缩归档往返试验，比较记录数、哈希、人物/决策查询及分支截止行为。
3. 试验 restic 对两个一致快照的真实新增空间，并恢复到新目录验证；旧备份在验证前保留。
4. 达到持续归档规模后，引入 Batch Worker；拆表迁移复杂时引入 Migrations；出现统计瓶颈后再评估 Aggregate。

本研究未给出可直接执行的删除或迁移命令。归档格式、版本兼容、故障重试、引用回收及查询接入均须在实施阶段验证，不能因采用成熟组件而省略。
