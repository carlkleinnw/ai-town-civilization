## 已实现

- 世界主文档只保存标量状态及分块清单；数组每 24 项一块，人物每人一块。变化检测只写变化的数据块，清单与数据块在同一事务提交。世界列表摘要独立保存，不随每秒时钟预算重复写入。
- 旧世界可直接读取；运行中世界在下一次真实持久化时切换新格式，暂停世界可逐个迁移。迁移不推进模拟、不裁剪原始状态。
- 命名存档使用 gzip 无损压缩，旧存档仍能打开。所有新存档和历史块包含格式、原始字节数及校验值，解压失败时明确报错，不返回残缺历史。
- 超过最近 180 个模拟日的历史按页压缩，原表保留 ID、日期、类型、索引和压缩块引用。历史、人物、计划、祖先查询透明解压，分支沿用祖先日期和序号截止。进行中的计划与决策不压缩，压缩不划算的小记录保留原样。
- 每天北京时间 11:20 调度一次历史压缩。它保留精确历史，不以年度摘要替代原始数据；不提供尚未实现的逐小时回放。
- 复用现有 Convex 分页、调度与事务骨架，以及 `fflate@0.8.2` 的纯 JavaScript gzip。此规模无需再引入独立队列、云存储或 Batch Worker 组件。
- restic 原生 Windows 工具放在 `E:/AI_town/tools/restic`，缓存、临时文件均在 E 盘。备份与启动器共用排他锁，备份期间通过启动器启动会被拒绝。

## 常用入口

在项目目录执行：

```powershell
npm run storage:status
npm run storage:migrate
npm run storage:archive
npm run storage:backup
npm run storage:index-history
```

`index-history` 在暂停世界上按批建立派生数字排序索引，不改原历史正文、ID 或创建时间；维护前先做完整备份。旧快照未升级时仍兼容读取，但可能扫描较多旧记录。需要受保护的完整备份可执行 `npm run storage:backup -- --critical`。保留策略在根目录 `storage-policy.json`，关键快照登记在 `storage-protected-backups.json`；两者随备份保留。

`status` 输出主数据库文件大小、E 盘可用空间和各世界新格式的累计写入次数、估算序列化字符数，保存到 `.runtime/storage/status.json`。字符数是负载估算，不等于数据库实际写入字节或磁盘日增长量。比较不同时间的报告才能测增长。

`migrate` 一次一个世界地切换存储格式并压缩旧命名存档；比较所有暂停世界迁移前后的完整状态。重复执行不会再次迁移已经切换的世界或存档。

`archive` 分页压缩旧历史，逐页事务提交，失败后可重新执行；已完成的压缩不会重复。它对暂停世界核对归档前后的历史查询与祖先结果。索引 stub 仍保留，因此精确查询无需启动额外文件服务。

`backup` 通过原 Windows 启动器停止项目，将完整 `.convex` 和配套源代码、配置备份到 `E:/AI_town/backups/restic`，随后检查仓库并请求恢复服务。依赖、运行缓存、构建产物与 `.git` 不重复备份。启动中的服务或来源不明的后端会阻止备份。代码版本另由 Git 管理；第一次改造前的备份另含 Git bundle。

restic 的本地密码文件位于 `E:/AI_town/backups/.restic-password`，Windows 权限限定为当前用户。它不写入源码、运行日志或备份仓库；保管此文件才能恢复加密备份。备份工具不会自动删除旧恢复点。需要更换工具路径时，可设置 `AI_TOWN_RESTIC` 指向经过校验的原生可执行文件。

## 恢复与回滚

修改前的一致性备份：`E:/AI_town/backups/before-storage-optimization-20261026`，包含原始代码、完整 `.convex`、Git bundle、未提交补丁和文件 SHA256 清单，SQLite `quick_check=ok`。

恢复到原版时，先停止项目，将当前代码和数据另存，再一起恢复该备份中的代码和 `.convex`。旧代码不认识新分块格式，不能只回滚代码。不要混用不同时间的主库、日志文件或外部 blob。

恢复 restic 快照时，先恢复到新的 E 盘目录，验证完整目录与 SQLite，再使用配套代码启动。不要直接覆盖正在运行的库。仓库 `check` 通过不等于项目已经恢复验证；最终交付报告单独记录实际恢复证据。

## 关于文件大小与版本回收

本次还执行了一次官方逻辑恢复：通过 `convex export --include-file-storage` 生成标准快照，在隔离后端用官方 `convex import` 恢复，核对 23 张业务表的 35,912 条记录后再切换。主库切换时从 2,224,558,080 字节降为 140,230,656 字节，减少 93.7%。完整原物理库留在 `E:/AI_town/backups/before-logical-rebuild-20261026/optimized-original.convex`；官方逻辑快照是 `E:/AI_town/backups/storage-optimized-logical-20261026.zip`。

逻辑快照保留业务表，不迁移原来的后端内部历史版本、历史任务队列或源码部署。源码和四项 Ollama 环境配置已重新部署，文明的一个原运行世界已恢复运行，原先暂停的 28 个世界保持暂停。已在恢复后对所有 29 个世界核对完整状态，确认没有离线追赶。原聊天小镇在本次操作前已不活跃，未擅自启动它。

压缩旧业务内容、拆分高频状态，降低的是后续写入与有效数据占用。旧的技术版本仍会遵守 Convex 自身保留窗口，因此刚迁移完文件可能继续变大，不能把当天文件变大直接判断为优化失败。

当前对应后端 `precompiled-2026-10-10-72ce13c` 的源码默认保留文档旧版本 14 天。本次未修改生产 `DOCUMENT_RETENTION_DELAY`；六小时窗口在隔离副本上尚未完成启动和回收验证。官方提交 `2ffe557` 提供 SQLite 分页加载的候选修复；本次核对的最新发布包仍为 72ce13c，该提交与主分支分叉，不能声称升级就能获得修复。不要直接 SQL 删除内部版本或修改回收游标。

完成回收后，SQLite 可以重用空闲页，文件不一定立即缩小；是否离线整理需根据空闲页和额外临时空间决定。单次 gzip 压缩率与 restic 写入量均不能推算整库长期节省比例。
