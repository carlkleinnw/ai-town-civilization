# 本机副本与技术数据生命周期（2026-10-27）

本轮保留当前 Convex、六小时技术版本窗口、文明规则、完整历史和命名存档。不升级压缩算法，不直接修改数据库内部记录。

## 已启用的规则

| 数据 | 规则与触发时机 |
| --- | --- |
| 当前世界、用户存档、业务历史 | 不参与技术文件清理 |
| 后端持续日志、后台启动输出、删除校验错误日志 | 每个当前文件最多 8 MiB，另留 3 个轮换文件；写入时执行 |
| 运行趋势 | 当前文件最多 4 MiB，另留 3 个轮换文件；图表跨轮换读取最近 1440 条，读取预算最多 8 MiB |
| 指定临时目录 | 启动器取得锁、启动子进程前，清理 `.runtime/temp` 和 `.runtime/storage/temp` 中整个子树七天未修改的项；有链接则拒绝清理 |
| 普通完整 restic 快照 | 每次完整备份成功、仓库检查通过后，按实际 `storage-policy.json` 回收；当前至少最近 2 份、7 天，两项均不满足才成为候选 |
| 关键快照、已验证恢复点、其他来源快照 | 保护，不按普通策略回收 |
| 旧独立目录与 ZIP | 继续只预览，不自动删；含迁移前的关键回滚资料 |

日志限制针对上述持续追加入口；既有一次性测试报告保留。若升级前已有超大技术日志，第一次轮换原样留作一个旧归档，随后按轮换次数淘汰。轮换日志是技术诊断记录，不是文明历史。

过期临时数据按修改时间判断，不按 Windows 通常未更新的访问时间。目录本身很旧、但子文件近期更新时仍保留。缓存并非整个 `.runtime`：后端程序、浏览器测试工具、验证证据、模型与依赖不会因七天规则被删。

## 普通备份回收的保护与恢复

回收限定为本机同一项目路径、`ai-town-complete` 标签的完整快照，并按备份主机分组。未知来源、无效 ID/时间不会删除；`critical`、`before`、`migration` 标签以及保护登记中的 ID 不回收。

`storage-verified-restores.json` 保存实际恢复验证凭据，随项目一起备份。至少一个已验证且仍存在的完整恢复点是启用回收的前提；凭据所指快照本身也受保护。回收使用 restic 的 `forget`、`prune`，最后再次 `check`，不手删仓库 pack 文件。`prune` 或后续检查失败会保留 pending 状态，下次备份重试；单次备份状态与回收状态分别保存。

这些规则不会限制关键快照的总量，也没有设置整个世界数据库的硬容量上限。保留完整业务历史仍会合理增长。六小时版本回收的长期负载验证继续是独立任务。

## 本轮旧副本处理

`scripts/retire-probes.ps1` 的明确名单仅覆盖 19 个已结束的存储/运行试验目录，保留 `tmp/pdfs` 和 `tmp/progress-storage-probe`。执行顺序：

1. 核对绝对路径为 `E:/AI_town/tmp` 直接子目录，无进程使用；识别共用依赖的目录链接。
2. 生成排除可再生 `node_modules` 的逐文件 SHA256 清单，备份到现有加密去重仓库，标为 `critical-retired-probes`。
3. 实际恢复整个快照并由 restic 校验，再对源文件和恢复文件逐项核对 SHA256。
4. 仅解除已核实指向正式依赖的目录链接，保留链接目标；删除名单内原副本及本次恢复验证目录。

实测覆盖 4374 个文件、11149320634 字节（约 10.38 GiB）；仓库新增压缩数据 148490864 字节（约 141.61 MiB）。这同时使用了仓库已有的内容去重与既有压缩，不能当成新压缩算法的收益。先前目录扫描重复计算了 13 个依赖目录链接，因此 13.27 GiB 不是可释放空间承诺。

可恢复快照：`f95c79385d7e3c076da714c996d15f9f5c98dc11342b7714ab8af3171333ca58`。恢复应使用仓库密码文件，通过 `restic restore <快照ID> --target <新的E盘隔离目录> --verify`，不要覆盖正在使用的数据。排除的依赖须按配套项目版本重新准备。

脚本默认只列名单；`npm run storage:cleanup-probes -- -Apply` 才执行归档、恢复、比对和清理。它不按目录名前缀删除新目录；今后新增试验需明确登记、复核并保留恢复证据。
